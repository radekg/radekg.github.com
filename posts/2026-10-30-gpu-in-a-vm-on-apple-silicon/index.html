GPU in a Linux VM on Apple Silicon

making Vulkan enumerate inside a krunkit VM
 October 30, 2026  3172  15 mins

I have been running the pi coding agent (a CLI that drives an LLM to read code, edit files, run commands) in a Linux VM on Apple Silicon for a while now. For an agent, to write working software operarting in real world, the agent must have the freedom to navigate in said world. More complex tasks, for example browser applications or extensions, require the agent to operate the software, like we do. Writing a Kubernetes operator is the best done when the agent can run what it’s building in a real Kubernetes cluster. It needs to trip over the hurdles on its own, like we do.

§give ’em all

Macs come with capable GPUs. But GPUs in Linux VMs on macOS are the tough part. Most people, including me until recently, assume a Linux VM on macOS gets no graphics acceleration. There is no display attached, no X server, no desktop. Not even Docker supports GPU in containers on macOS!

Whether it is a browser application, or local LLM inference, a working GPU supplements any development environment for an autonomous agent. When an agent needs to run a model—llama.cpp (the C/C++ inference engine most local LLM tools are built on), Ollama (a model registry and local API server that wraps llama.cpp), anything that does on-device inference—that runtime uses the GPU. For an agent on the macOS host, this is straightforward: same machine, same GPU.

I want to run the agent inside a VM, fully isolated, so the harness cannot reach back into the host. The only way to keep that isolation and still have GPU compute available to the agent is to pass the GPU through the VM. The place where I have seen the mention of a Linux VM on macOS + the GPU was in Colima, the colima model command. Since I knew it was possible, I wanted to figure out how to do this myself on Apple Silicon. This is the story of how that happened, and the chain of issues that made it possible.

As a bonus, anything Vulkan works inside the guest. That is useful in its own right. Building or testing front-end apps that use GPU paths, for example. But it is not the main reason this exists.

Lima is a tool for running Linux VMs on macOS, originally written for container-style workflows. This is not a job for Lima alone because Lima by default offers no GPU passthrough on macOS. It is also not a job for QEMU VM—the most common open-source machine emulator and virtualizer, because QEMU on macOS does not get access to the GPU either. However, there is one gem out there. The one Colima uses: krunkit, a thin macOS frontend over libkrun. Likrun is the library that talks to Apple’s hypervisor.framework, the macOS API for creating and managing virtual machines. Krunkit is the only thing on this platform that exposes a virtio-gpu device (a virtual GPU that the guest sees as a virtio peripheral, with rendering offloaded to the host) backed by something useful on the host side. So:

I will need:

  • krunkit on the host (Apple Silicon macOS).
  • a custom-built Mesa guest (Mesa is the open-source graphics stack; here, built with only the virtio-vulkan driver enabled, the Vulkan driver that talks to the host over the virtio-gpu wire).
  • a slp/krun-pinned virglrenderer on the host (virglrenderer is the host-side renderer that turns the guest’s virtio-gpu commands into calls on the host’s actual GPU; the slp/krun tap is a Homebrew tap, i.e. a third-party package source, that ships a version known to work with krunkit).
  • a small, ugly patch. Without it, nothing enumerates.

That fourth item is the entire subject of this post.

I will cover:

  • the stack, end to end.
  • the symptom that started the investigation.
  • one GitHub comment that changed everything.
  • the root cause analysis that came after.
  • the patch that fixed it.
  • the upstream fix that will eventually make the patch unnecessary.

§background

The stack looks like this:

┌──────────────────────────────────────────────────────────────────┐
│  Ubuntu 24.04 aarch64 guest                                      │
│                                                                  │
│   pi coding agent + Chromium, llamma.cpp, Ollama, ...            │
│                    │                                             │
│                    ▼                                             │
│   Vulkan apps   ──▶   Venus ICD (Mesa, virtio-vulkan only)       │
│                    │                                             │
└────────────────────│─────────────────────────────────────────────┘
                     │  virtio-gpu / Venus protocol over shared mem
                     ▼
┌──────────────────────────────────────────────────────────────────┐
│  macOS host (Apple Silicon)                                      │
│                                                                  │
│   krunkit / libkrun  ──▶  virglrenderer  ──▶  Metal              │
│                                       (slp/krun tap, pinned)     │
└──────────────────────────────────────────────────────────────────┘

On the guest side, krunkit exposes a virtio-gpu device with a Venus-compatible transport. Venus, in this context, is a protocol for running Vulkan across the virtio-gpu boundary: the guest translates Vulkan calls into a wire format the host can execute, and the host executes them on the real GPU. Memory for Vulkan buffers and command rings is shared between the guest and host via the RESOURCE_CREATE_BLOB ioctl, an ioctl being a syscall for sending a command to a device driver, here the virtio-gpu driver in the guest kernel. The guest Mesa is built from source with -Dvulkan-drivers=virtio only. No GL, no GLX (the two historical Linux OpenGL transports), no EGL (the interface between OpenGL/Vulkan and the windowing system), no Gallium drivers (Mesa’s internal driver framework). The build is installed to /opt/mesa/venus. The guest points VK_DRIVER_FILES. VK_DRIVER_FILES is the environment variable that tells the Vulkan loader which Installable Client Drivers to consider. IDCs are the per-driver JSON manifests the loader discovers and dlopens. The one created by this build is virtio_icd.aarch64.json and that is the only Vulkan ICD the loader sees.

On the host side, virglrenderer translates the guest’s Vulkan commands into Metal calls. Metal is Apple’s graphics API, the only way to talk to the GPU on macOS. This virglrenderer must be the version pinned by the slp/krun Homebrew tap. The upstream Homebrew virglrenderer 1.3.0 is incompatible with krunkit on Apple Silicon and produces the most unhelpful error imaginable. There is a fix-virglrenderer.sh script for exactly this situation. Use it. It removes the invalid virglrenderer and installs the slp/krun-pinned one.

So far, this is all ground that’s already been explored. But how did we get there?

§the symptom

Run a stock Ubuntu 24.04 cloud image with the system Mesa inside a krunkit VM and:

$ vulkaninfo
ERROR at ./vulkaninfo/./vulkaninfo.h:458:vkCreateInstance failed with ERROR_OUT_OF_HOST_MEMORY

vkCreateInstance is the first Vulkan call every program makes. It sets up the library and lets the loader pick an ICD. ERROR_OUT_OF_HOST_MEMORY is the loader’s way of saying “something inside the ICD bailed out”. Or, depending on the version:

ERROR: [Loader Message] Code 0 : setup_loader_term_phys_devs:  Failed to detect any valid GPUs in the current config
ERROR at ./vulkaninfo/./vulkaninfo.h:245:vkEnumeratePhysicalDevices failed with ERROR_INITIALIZATION_FAILED

vkEnumeratePhysicalDevices is the second Vulkan call. It lists the GPUs the loader can see. ERROR_INITIALIZATION_FAILED is the catch-all “the ICD is broken” error.

Either way, no GPU. Stock Debian, Ubuntu, Fedora. All the same. This is a real problem because if you actually want to do anything Vulkan in a krunkit VM, you cannot use a stock image.

The investigation that produced the answer is documented in two issues on the krunkit repository, and the chain between them is short enough to read in order.

§issue #102

libkrun/krunkit#102[1] is the symptom report. A user runs ghcr.io/ggml-org/llama.cpp:light-vulkan inside a krunkit VM. The container ships a recent Mesa. vulkaninfo fails. No GPU is detected. The error is vkCreateInstance failed with ERROR_OUT_OF_HOST_MEMORY. That’s exactly the error I have become intimate with.

The user does all the right debugging. They check the capset (the capability set the host advertises over virtio-gpu to say which features it supports), the parameters, the protocol version. Venus negotiates fine. VIRTGPU_PARAM_HOST_VISIBLE reports 1, i.e. yes, the host supports making blobs visible to both sides for sharing. The issue is closed by switching to a container image whose Mesa carries a downstream patch. The workaround exists. The root cause, at this point, is not pinned down.

This is where most investigations end. Someone finds a workaround, the issue is closed, life goes on.

§the comment that pointed the way

It did not end here because @stewartjeacocke left a one-line comment[2] on issue #102:

I believe the root cause of this may be libkrun/krunkit#114[3].

This single sentence changes everything.

§the root cause

Issue #114 is the diagnosis. The author did the work I would have wanted to do. The finding is:

On macOS on Apple Silicon, the VM page size—the granularity at which the hypervisor maps memory between guest and host—is 16384 bytes. Apple’s hv_vm_map requires page-aligned arguments. libkrun’s resource_map_blob passes the guest-requested blob size unchanged into hv_vm_map. The guest runs on 4 KiB pages. The guest kernel PAGE_ALIGNs blob sizes up to a multiple of 4096 (the kernel macro that rounds a size up to the nearest page boundary). But that is not a multiple of 16384. Remember, on macOS it must be a multiple of 16384 and 4096 is simply less. So the host-side mapping fails with EINVAL—the standard POSIX error code for “invalid argument”. The guest’s mmap (the syscall that maps a file or device region into the process’s address space) returns EINVAL. Mesa’s Venus ring shmem is 131268 bytes; the kernel rounds it to 135168; 135168 is 33 × 4 KiB and 8.25 × 16 KiB. The mapping fails. Venus reports the failure upward as VK_ERROR_OUT_OF_HOST_MEMORY, and the Vulkan loader aborts vkCreateInstance.

The author of #114 includes a self-contained C reproducer that walks a list of sizes and shows the exact failure pattern. Sizes that are multiples of 16384 work. Sizes that are not, do not. It does not matter what the guest’s page size is and what the protocol says. The host is imposing an undocumented requirement and reporting it as a generic ErrUnspec (the libkrun catch-all error variant), which surfaces to userspace as a bare EINVAL with no indication of the cause.

Not much to add to that analysis.

§the fix

The fix lives in slp’s downstream Mesa fork, in commit 761ef1ec[4]. It does exactly what the issue title suggests: it forces Venus allocations to be multiples of 16384. The change is in four call sites:

  • src/virtio/vulkan/vn_device_memory.c — vn_device_memory_alloc_simple aligns the allocation size up to 16384.
  • src/virtio/vulkan/vn_renderer_virtgpu.c — virtgpu_bo_create_from_device_memory and virtgpu_shmem_create align their sizes up.
  • src/virtio/vulkan/vn_ring.c — vn_ring_get_layout aligns the ring shmem size up.

The author of #114 is explicit that all four hunks are needed. The vn_ring.c one alone gets past vkCreateInstance, then device memory allocation fails instead. Drop any one hunk and the failure moves somewhere else.

§what this enables

Once the four-hunk patch is in place, the guest Mesa enumerates a real Vulkan physical device. In my case, on an M-series host, that device reports itself as Virtio-GPU Venus (Apple M5 Pro). From that point on, anything that talks to Metal on the host has a Vulkan-backed implementation in the guest.

The main thing this enables is local LLM inference from inside the agent. llama.cpp, Ollama, vLLM (a high-throughput inference server for serving LLMs to many clients), MLX (Apple’s array framework for running ML models on Apple Silicon), or WebGPU, anything that talks to the GPU on macOS works as if it were running on the bare host, except it is running in the VM, alongside the agent. This is what makes it possible to test “computer + LLM” deployments end to end on macOS without ever leaving the host machine: the agent is fully sandboxed in a VM, the GPU is passed through, and any local-inference runtime the agent wants to use just works.

A second thing is that the guest is not a server-class VM. It is a desktop-class VM with a real GPU. Anything Vulkan-based runs inside it. This is handy for front-end work—building or testing apps that use GPU paths (WebGPU, Skia/Vulkan, canvas-heavy UIs)—and Chromium picks up hardware acceleration as a side effect.

A third thing, and this one surprised me, is that nested virtualization is enabled in the image. KVM (the Linux in-kernel hypervisor, normally requires hardware virtualization extensions on the host CPU) is available inside the guest. So the guest can itself host additional VMs or run workloads that need /dev/kvm. This is unusual for a krunkit VM and I am not sure why it works on this combination, only that it does. I was able to run Firecracker microVM inside. I am certain it is possible to further pass the GPU to Firecracker itself. But that’s a bed time story for another day.

§the recipe, in summary

The recipe that works, on Apple Silicon, today:

  • install krunkit, libkrun, libkrunfw (a firmware bundle used by libkrun), gvproxy (the network plumbing used by Lima to give the guest a routable network), and virglrenderer from the slp/krun Homebrew tap. Trust the formulae (Homebrew 4.x removed automatic trust for third-party formulae; brew trust opts back in). Do not use the upstream Homebrew virglrenderer.
  • build a guest Mesa with -Dvulkan-drivers=virtio only.
  • apply the four-hunk 16384-alignment patch before building.
  • install the result to /opt/mesa/venus and point VK_DRIVER_FILES at the Venus ICD.
  • inside the guest, run vulkaninfo --summary and see Virtio-GPU Venus (Apple Mx Pro).

The recipe is a bit fragile, it’s probably wise to hold forks of all dependencies. There is the Mesa patch that is not in upstream Mesa. And there is the virglrenderer version that is not in upstream Homebrew.

§the upstream solution

Hardcoding 16384 is a workaround for an undocumented host-side requirement. The proper fix landed in upstream Mesa as MR #44783 “venus: honor the virtio-gpu blob alignment”[5], merged on 2026-09-28 by Matthew Periut.

Instead of hardcoding 16384, MR #44783 queries the kernel for VIRTGPU_PARAM_BLOB_ALIGNMENT—a new parameter added in Linux 7.2—and rounds blob sizes up to whatever the kernel reports. On hosts without that parameter it falls back to 1, i.e. no rounding. The change is a no-op on every other platform.

The implementation is a single hunk in vn_renderer_virtgpu.c. It is much smaller than the slp downstream patch because it does not hardcode anything. It just listens to the kernel.

This is the kind of fix that makes the slp downstream patch obsolete eventually. The downstream patch exists because, at the time, the kernel did not advertise its alignment requirement. Once both Mesa and the kernel are new enough, the patches for those new versions aren’t required anymore.

The conditions for no patch needed:

  • a Mesa release that contains MR #44783,
  • a Linux 7.2+ guest kernel,
  • Ubuntu 24.04’s HWE kernel with kernel 7.2 support. At the time of writing it is 24.04.5 LTS (HWE) with kernel version 7.0.

The third of these is the bottleneck. Installing an edge kernel could be an option.

§closing words

The investigation that produced it was carried out, almost entirely, by two people in two GitHub issues and one commit. That is how good open-source debugging actually happens: small, focused, well-documented. The fact that I can run a Linux VM with a working GPU on Apple Silicon is a direct consequence of those two issues and one patch.

Once the upstream fix rolls through Ubuntu’s HWE kernel, the hardcoded patch becomes unnecessary.
